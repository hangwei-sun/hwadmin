# HwAdmin 前后端接口契约与通信协议规范

本规范确立了 HwAdmin 所有 HTTP 接口（包括 `/adminapi` 后台接口、`/api` 前台开放接口、插件路由）的统一数据传输格式、状态码约定与高级列表筛选协议。

---

## 一、统一响应数据结构

所有接口必须统一返回 JSON 格式，顶层结构严格遵循以下规范：

```json
{
  "code": 1,
  "msg": "操作成功",
  "data": {},
  "time": 1700000000
}
```

### 字段含义定义：
- **`code`** (整型)：业务状态码。
  - `1`：**成功**（业务处理顺利完成）。
  - `0`：**通用业务失败**（如“验证码错误”、“库存不足”、“请先选择记录”等）。
  - `401`：**未登录或凭据失效**（前端触发跳向登录页）。
  - `403`：**无权限访问**（前端提示无权限拒绝访问）。
  - `其他自定义错误码`：用于特定业务约定的细分场景。
- **`msg`** (字符串)：面向终端用户或开发者的提示信息。
- **`data`** (任意类型)：业务负载数据（对象、数组、标量或 `null`）。
- **`time`** (整型)：服务端当前时间戳（秒级）。

---

## 二、列表分页数据结构铁律

凡是列表类接口（例如 `index` 操作），其 `data` 节点**必须且只能**采用如下结构：

```json
{
  "code": 1,
  "msg": "ok",
  "data": {
    "list": [
      {
        "id": 1,
        "title": "示例文章标题",
        "create_time": 1700000000
      }
    ],
    "total": 100
  },
  "time": 1700000000
}
```

> **注意**：
> 1. 数据列表键名必须固定为 **`list`**，严禁使用 `rows`、`items`、`data` 等混乱别名。
> 2. 总条数键名必须固定为 **`total`**（整型）。
> 3. 后端调用方式：`Result::page($list, $total);`。

## 三、高级列表筛选协议 (`QueryParams`)

HwAdmin 采用一套高度统一、安全白名单过滤、开箱即用的结构化列表查询参数协议：

### 1. GET 请求参数规范

| 参数名 | 类型 | 默认值 | 说明与示例 |
| :--- | :--- | :--- | :--- |
| `page` 或 `pageNo` | 整数 | `1` | 请求的分页页码，从 1 开始 |
| `limit` 或 `pageSize` | 整数 | `20` | 每页返回记录数，系统最大限制为 `500` |
| `sort` | 字符串 | 默认主键或控制器指定 | 排序字段名称，例如 `sort=create_time` |
| `order` | 字符串 | `desc` | 排序方向，仅允许 `asc` 或 `desc` |
| `keyword` | 字符串 | 空字符串 | 快速模糊搜索词，自动匹配控制器 `$searchFields` |
| `filter` | JSON 字符串 / 键值对 | 空 | 字段过滤条件，例如 `filter={"status":"1","cate_id":"2"}` |
| `op` | JSON 字符串 / 键值对 | 空（默认 `=`） | 字段对应的比较操作符，例如 `op={"title":"like","status":"="}` |

### 2. 支持的操作符清单 (`op`)
- `=`：等于（默认）
- `<>` 或 `!=`：不等于
- `>` / `>=` / `<` / `<=`：数值大小比较
- `like`：模糊匹配（服务端自动安全追加 `%keyword%` 转义）
- `not_like`：非模糊匹配
- `in`：包含（值使用逗号隔开，例如 `"1,2,3"` 或数组 `[1, 2, 3]`）
- `not_in`：不包含
- `between`：区间（值用逗号隔开，例如 `"10,50"`）
- `not_between`：区间外
- `null`：为 NULL
- `not_null`：不为 NULL
- `find_in_set`：FIND_IN_SET 匹配

### 3. 安全防护白名单机制
服务端 `core\crud\QueryParams::apply()` 会在执行前读取当前模型对应真实物理表的所有列（`$fields`），**未在数据表中真实存在的查询参数或非法操作符将被直接静默丢弃**，杜绝任何通过 URL 参数恶意拼接注入的风险。

## 四、HTTP 状态码与业务码对应表

| 场景 | HTTP Status | Response `code` | 说明 |
| :--- | :---: | :---: | :--- |
| 业务成功 | 200 | `1` | 成功返回数据 |
| 业务逻辑受阻（校验不通过） | 200 | `0` | 正常请求但业务不允许，msg 返回原因 |
| 未登录 / Token 过期 | 200 或 401 | `401` | 凭证失效，通知前端清空状态并跳转登录 |
| 权限不足 | 200 或 403 | `403` | 当前角色未配置对应节点权限 |
| 资源不存在 | 200 或 404 | `0` | 如 `findOrFail` 未查到数据 |
| 服务端致命错误 | 500 | `0` | 系统发生未捕获异常，生产环境自动脱敏 |
